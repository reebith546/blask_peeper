# Black Pepper Flower Bar — «Цветы с характером»

Интернет-магазин цветов на Django для Алматы.

## Приложения

- `catalog` — категории и товары
- `orders` — заказы и позиции заказа
- `payments` — онлайн-оплата через TipTop Pay / SmartCore (редирект на форму + подписанный callback)
- `delivery` — зоны доставки (упрощённая MVP-версия: районы города с фиксированной ценой)
- `content` — редактируемые блоки главной страницы (Hero, Instagram, промо)
- `reviews` — отзывы клиентов с модерацией
- `accounts` — роли доступа в админке и раздел «Сотрудники»
- `audit` — журнал действий персонала (аудит) и аутентификации
- `main` — общие вьюхи сайта (главная страница)

## Запуск локально

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
```

Заполните `.env` реальными значениями (минимум — параметры подключения к PostgreSQL).

Поднимите PostgreSQL. Проще всего — через Docker (нужен запущенный Docker Desktop):

```bash
docker compose up -d
```

Это создаст контейнер с базой `blackpepper` на порту 5432 (имя/порт берутся из `.env`),
данные сохраняются между перезапусками в volume `postgres_data`. Если PostgreSQL уже
установлен у вас локально другим способом — просто убедитесь, что он запущен и в `.env`
указаны верные параметры подключения, `docker-compose.yml` тогда не нужен.

```bash
python manage.py migrate
python manage.py createsuperuser
python manage.py setup_roles
python manage.py runserver
```

`setup_roles` создаёт роли доступа в Django Admin — три уровня:

- **Владелец** (superuser) — видит и может всё, без ограничений; в «Журнале
  действий» видит вообще все события (все роли, системные записи).
- **Директор магазина** — товары, категории, заказы, блоки главной страницы,
  отзывы (без удаления), раздел «Сотрудники» и «Журнал действий» (только
  просмотр). Доставка, платежи и системные разделы ему недоступны.
- **Продавец** — заводится директором через раздел «Сотрудники»; при создании
  директор выбирает роль (Продавец / Директор) и, для продавца, отмечает
  разделы («Каталог», «Заказы», «Отзывы», «Контент главной»). Журнал действий
  продавцу недоступен.

### Раздел «Сотрудники»

Директор ведёт всю команду в одном разделе — и продавцов, и других директоров.
Ограничения: нельзя создать владельца, нельзя выдать произвольные Django-права
(только роль + разделы), нельзя деактивировать себя и последнего активного
директора, учётки не удаляются — только деактивируются.

### Журнал действий (аудит)

Приложение `audit`. Фиксирует действия персонала в админке и аутентификацию:
создание / изменение (с разбором «было → стало») / удаление, массовые действия,
вход / выход / неудачный вход, смену пароля, изменение ролей, а также каждый
заход на страницы админки. Заказы и отзывы, созданные клиентами на сайте, в
журнал не пишутся — это бизнес-данные.

- записи **неизменяемы** и **не удаляются** через интерфейс (ни у кого);
- **директор** видит действия продавцов и других директоров (не владельца и не
  системные события), **владелец** — всё;
- по умолчанию список показывает «значимые» события; просмотры страниц — по
  отдельному фильтру;
- выгрузка в CSV — из действий над списком.

Чистка старых записей (срок хранения — 24 месяца), в cron раз в сутки:

```bash
python manage.py cleanup_audit            # удалить старше 730 дней
python manage.py cleanup_audit --dry-run  # только показать, сколько попадёт
```

### Онлайн-оплата (TipTop Pay / SmartCore)

Приложение `payments`. Схема: сервер вызывает `initPayment` → клиент уходит на
форму оплаты шлюза → шлюз шлёт подписанный `callback` о результате → заказ
переводится в «Оплачен». Документация шлюза: https://docs.smartcore.pro

Оплата **включается автоматически**, когда в `.env` заданы `SMARTCORE_ACCOUNT`,
`SMARTCORE_MERCHANT_KEY`, `SMARTCORE_SECRET`. Пока их нет — чекаут работает
по-старому: заказ создаётся со статусом «Новый», менеджер звонит и принимает
оплату сам.

Когда оплата включена:

- на чекауте email становится обязательным (нужен шлюзу для чека);
- заказ создаётся со статусом **«Ожидает оплаты»**, клиент уходит на форму шлюза;
- по `callback` заказ становится «Оплачен» (флорист начинает сборку) либо
  «Ошибка оплаты» — тогда клиенту доступна кнопка «Оплатить снова»;
- в кабинете шлюза для callback укажите: `https://<домен>/payments/callback/`;
- в админке: статус платежа виден в списке и карточке заказа, действие
  «Проверить статус в платёжном шлюзе» у раздела «Платежи» сверяет статус вручную;
- изменения статуса по callback пишутся в «Журнал действий» как системные события.

Ручная проверка интеграции в песочнице — скрипт `smartcore_sandbox.py` в корне
репозитория (консольный, без Django).
